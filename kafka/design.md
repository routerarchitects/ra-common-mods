# Design Document: Common Kafka Module

## Overview

The `kafka` module provides a thin, explicit wrapper over IBM Sarama (`v1.62.0`) using `log/slog`, opt-in Prometheus metrics, and opt-in OpenTelemetry tracing. It keeps topic routing, group selection, and business handlers in the application while enforcing safe offset-acknowledgement, retry/DLQ, configuration validation, and shutdown invariants.

## Ownership & Architecture

- **`BrokerConfig`**: Cluster endpoints (`host:port`), `ClientID`, SASL/TLS authentication, and socket `DialTimeout` / `ReadTimeout` / `WriteTimeout` (30s defaults).
- **`ProducerConfig`**: `RequiredAcks`, `Idempotent`, `Compression`, `MaxRetries`, `RetryBackoff`, `MaxMessageBytes`, `Timeout`, `Partitioner` (`hash` / `crc32` / `murmur2` / `roundrobin` / `random`). Produces via `Producer` (`NewProducer`).
- **`ConsumerConfig`**: `GroupID`, `InitialOffset` (`oldest` default / `newest`), `ResetInvalidOffsets` (default `true`; when `false`, out-of-range offsets produce a terminal error instead of resetting), `IsolationLevel` (`read_uncommitted` default / `read_committed`), `BalanceStrategy` (`roundrobin`/`sticky`/`range`), `SessionTimeout`, `HeartbeatInterval`, `RebalanceTimeout`, `MaxProcessingTime` (Sarama internal message-channel backpressure, default `100ms`, not a handler deadline), `CommitMode` (`periodic`/`sync`), `CommitInterval`, `HandlerTimeout` (per-attempt deadline), `ShutdownTimeout` (graceful handler drain budget), `CloseTimeout` (Sarama teardown budget after drain, default `5s`).
- **`Consumer` (`NewConsumer`)**: Owns exactly one `sarama.ConsumerGroup` per `Run`, serving all pre-registered `Subscription` entries (`Topic`, `Handler`, `HandlerTimeout`, `RetryPolicy`, `Interceptors`). Multiple `Consumer` instances may coexist per process for hybrid group isolation.

## Delivery & Failure Model

1. **Sequential within a partition, concurrent across partitions**: `ConsumeClaim` processes messages synchronously in partition offset order without spawning detached per-message goroutines. Source `Message` slices and metadata must be treated as read-only; for DLQ-enabled subscriptions, an immutable snapshot is captured before any interceptor or handler runs.
2. **Explicit dispositions**: `processMessage` returns `outcomeProcessed`, `outcomeDeadLettered`, `outcomeDiscarded`, `outcomeInterrupted`, or `outcomeTerminalFailure`. Offsets are marked only for `outcomeProcessed`, `outcomeDeadLettered`, or `outcomeDiscarded` when `session.Context().Err() == nil`.
3. **Cancellation precedence**: Session cancellation (rebalance or shutdown) interrupts processing immediately and leaves unresolved offsets unmarked.
4. **Retries & DLQ**:
   - **A nil `RetryPolicy` is rejected at `Subscribe` time**; callers must explicitly choose a strategy.
   - Bounded retries run up to `1 + MaxRetries` attempts with capped exponential backoff and full positive-floor jitter (`[delay/2, delay]`).
   - `RetryStrategyDLQ` publishes the pre-handler snapshot with `x-original-*` metadata headers (`x-original-error` holds a safe failure classification). When DLQ publication fails, `DLQFailureDiscard` marks and continues, `DLQFailureRetry` retries only retryable DLQ writes with backoff, and `DLQFailureStop` stops the consumer without marking the failed offset. Known permanent publication errors also stop the consumer under `DLQFailureRetry` and leave the source offset unmarked.
   - `RetryStrategyStop` stops `Run` with a terminal error after exhausting retries, without publishing to a DLQ or discarding the message.
5. **No exactly-once claims**: Kafka commit and handler/DLQ side effects are separate operations; duplicates are possible on crashes or rebalances, so handlers must be idempotent.

## Lifecycle & Graceful Shutdown

- `Subscribe` registers and validates immutable subscription descriptors without broker I/O. Topic names are validated (1–249 chars, ASCII `[a-zA-Z0-9._-]`, not `.` or `..`).
- `Run` is single-shot: it transitions `Registered -> Starting`, creates one `sarama.ConsumerGroup` with a `cancelableDialer` wired to the per-`Run` context (failing fast and returning the wrapped error with `State=failed`, `Ready=false` if client creation fails—without an internal startup retry loop), drains `Errors()` continuously until client close, and runs `Consume` with jittered reconnect backoff for transient post-startup errors and immediate termination for unrecoverable errors (auth, config, unexpected closed group).
- **Readiness**: `ConsumerHealth.Ready` is set `true` only after all assigned partition claims have entered consumption for the current session, not merely after `Setup`. A member with zero assigned partitions is immediately ready. Readiness resets on rebalance, shutdown, and terminal errors.
- **Initial-offset semantics**: `InitialOffset` defaults to `"oldest"` in v0.2.0. New consumer groups replay all retained records if no committed offset exists. Existing valid committed offsets are authoritative and never reset. When `ResetInvalidOffsets = false`, an out-of-range committed offset stops `Run` with a terminal error rather than resetting to `InitialOffset`.
- On `Close()` or parent context cancellation, the admission gate closes before stop notifications, readiness updates, or logging. Admitted messages can finish within `ShutdownTimeout`. When the drain completes or expires, the consumer cancels its session and starts the `CloseTimeout` watchdog. If the watchdog expires, it closes the consumer's broker sockets, including any socket still waiting for a synchronous commit. Startup cancellation also uses the watchdog, since no claims have been admitted. `Cleanup` makes a best-effort commit in `CommitSync` mode, and `Run` waits for the Sarama client and its own goroutines to finish. Handlers and caller-owned dependencies can extend shutdown if they take longer to return.

## Observability & Driver Limitations

- **Safe diagnostics**: Library logs, `Health().LastError`, trace error events/status, and `x-original-error` emit bounded failure classifications rather than raw panic values or arbitrary handler errors; wrapped errors are preserved for callers (`errors.Is`/`errors.As`), and handlers/DLQ ACLs remain responsible for payload/application-log sensitivity. Use `kafka.WithErrorCode(err, code)` to attach a stable, bounded application-defined error code to handler errors; implement `kafka.SafeErrorCodeProvider` for structurally typed codes.
- **Metrics**: Registered explicitly on a caller-supplied `prometheus.Registerer` (`NewMetrics`), assuming at most one `Consumer` member per `group_id` per process for `kafka_consumer_ready`. Lag ownership is guarded atomically under `lagMu`. Sarama `session.Commit()` returns no error; `kafka_commit_errors_total` counts only positively identified commit errors from `Errors()`. `kafka_consumer_in_process_backlog` reflects the observed per-claim backlog (`HighWaterMarkOffset - nextOffset`) at the time a handler is invoked, with `kafka_consumer_backlog_updated_timestamp_seconds` recording the last update time; both are cleaned up per claim owner on `Cleanup`. This is **not** broker-committed consumer-group lag—use an external consumer-group lag monitor for authoritative production alerting.
- **Tracing**: Configured explicitly via `TracingConfig` (`TracerProvider` + `Propagator`), injecting/extracting W3C trace context on copied headers without touching globals.
- **Synchronous Producer**: Context cancellation is checked before JSON marshaling and before `SendMessage`, but in-flight synchronous Sarama sends cannot be aborted mid-call. Nil keys remain nil `sarama.Encoder` interfaces for Sarama random partitioning.
- **SASL/TLS validation**: SASL PLAIN credentials over non-TLS connections are rejected unless `SASLConfig.AllowInsecurePlaintext = true` (development only). Contradictory configs (TLS disabled with SASL credentials, partial cert/key pairs) are rejected at client creation time.
- **Bounded Sarama teardown**: `Metadata.Timeout` is bounded, `Metadata.Retry.Max` is set to 2, and `Consumer.Offsets.Retry.Max` is set to 1 to prevent unbounded metadata and coordinator retries from blocking shutdown after `CloseTimeout` has started.
